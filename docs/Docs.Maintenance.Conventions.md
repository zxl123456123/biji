# 文档维护与归档规范

本文档规定晴笺项目文档的职责、维护方式和归档边界。

## 文档内容原则

文档记录代码里不容易看出的设计意图、约束、权衡和真实进度，不逐行复述实现。当前事实必须使用“✅ 已实现”“⛔ 未实现”或“🕒 未来可能”明确标注，禁止把计划描述成现状。文档与代码默认使用中文说明，代码注释按已有风格保持简洁。

## 1. 目录角色与边界

- `README.md` 面向使用者，说明当前能力与运行方式。
- `docs/` 存放始终与实现一致的权威说明。
- `docs/current/` 只存放尚未完全落地的设计和实施计划。
- `docs/archive/` 只存放不再代表当前行为的历史资料。
- `AGENTS.md` 提供会自动进入协作上下文的当前约束与文档索引，不累积过期事实。

## 2. 归档命名规则

- 功能目录：`docs/archive/<YYYY-MM-DD>/<feature>/`。
- 独立文档：`docs/archive/<YYYY-MM-DD>/<BaseName>.history.md`。
- 归档内容默认不可继续作为当前规范维护。

## 3. 归档前的 AI 职责

归档前必须核对代码，把仍有效的结论上收到 `README.md` 或对应架构文档；在原文顶部写明归档原因、当前权威文档和使用限制；更新所有把历史文档当作当前入口的链接。目录级归档保持原目录结构，除状态说明外不改正文。

## 4. 链接与引用的推荐约定

当前行为链接到 `README.md` 或 `docs/` 权威文档，进行中设计链接到 `docs/current/`，历史背景才链接到 `docs/archive/`。新增、合并或归档架构文档时同步更新 `AGENTS.md` 索引。

## 5. AI 操作提示

文档结构调整前先给出处理清单和章节提纲。功能完成后同步受影响的权威文档和更新记录；有实际文档改动时随代码提交，不添加任何 AI 署名。不得擅自删除或归档仍可能代表当前行为的资料。
