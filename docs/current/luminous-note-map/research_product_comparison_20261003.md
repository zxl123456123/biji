# 同类笔记软件补充调研

日期：2026-10-03。来源：用户要求查阅同类软件，评估界面、易用性与性能的优化空间。

本文件是只读调研记录，不是已实施方案，不改变现有 MVP 验收状态。本轮只新增本文件，没有修改应用源码、用户数据或 Windows 制品。

## A. 系统边界与现有能力

- ✅ 已实现：本地笔记、所见即所得编辑、草稿、标签、组合筛选、网格/日期排版、回收站、生活账本、主动提问的 AI 面板。
- ✅ 已实现：每条有效记录对应一个关联图节点；共同标签与本地词面相似分别解释；Canvas 光流、主题与动效开关。
- ✅ 已实现：大图计算 Worker 请求边界、图模块延迟加载、卡片每批 60 条、绘制像素与帧率上限。
- ⛔ 未实现：编辑历史、导入预览/合并选择、完整标签管理、每日回顾、可搜索的快速打开面板、局部图谱模式、时间轴回放。
- ⛔ 未完成验收：全部编辑/安全交互、真实大任务 Worker、原生拖拽/触屏/IME、GPU 与桌面长时间运行。见 [发布记录](../../Release.Verification.0.5.0.md)。

## B. 入口与主流程

- `src/App.tsx` 协调记录/关联图/账本、搜索、编辑弹窗及保存；`src/NotesView.tsx` 展示过滤后的笔记。
- 搜索是当前数组的正文子串匹配，并可叠加精确标签与未完成条件；Ctrl K 聚焦搜索框，没有快速打开结果面板。
- 保存修改先更新 React 状态并显示提示，effect 再写浏览器存储和调用桌面保存；提示不是 SQLite 已落盘的证明。
- 两个保存 effect 分别监听笔记与账目，但都提交完整笔记和账目快照。桌面 `save_data` 在事务内删除两张表的全部行，再逐行插入。
- 图谱输入是全部有效记录的 id/content；正文变化后提交完整输入构建关系，界面筛选再投影节点与边。普通主题变化不会提交新关系计算。

### 性能与技术边界

- flomo 认知地图官方说明当前按月刷新，单次随机载入最多 5000 条。这是它的产品限制，不能当作晴笺可实时重算任意数量记录的证据。
- Joplin 搜索文档说明 FTS4 对中日韩等无空格分词语言有局限，使用另外的搜索模式，大集合可能更慢。不能推导“用了 SQLite 全文索引，中文短词搜索一定快且完整”。
- SQLite FTS5 的 trigram 支持子串，但少于三个 Unicode 字符的 MATCH 子串不命中；LIKE/GLOB 有无法用索引而回退扫描的情形。中文一/二字检索必须单独评估。
- 晴笺目前是 n-gram TF-IDF 词面相似，不是向量语义模型；同类产品的语义聚类效果不可直接视为现有能力。
- 既有本地随机汉字夹具记录：100/500/1000 条的 Node 构图 p95 为 110.97/881.34/2188.19ms；500条≤300ms候选仍未达到。本轮只核对已有记录，未重跑基准，不能代替真实 Worker 等待、输入响应或 GPU 帧耗时。
- 既有包体候选也未达到：初始加图相对 S1 至少增加 27.51KB gzip，Worker 另计，候选为 25KB。见 [r2 评审](review_notes_impl_r2_1.md) 与 [现场观察](ui-observations.md)。

## G. 不确定点清单

- U1：真实用户是否更偏好日记式日期浏览、卡片或列表？需用同样的找回/编辑任务试用比较。本轮没有用户测试，视觉与效率判断仅为启发式评估。
- U2：实际数据量、长正文和共用标签下的构图耗时、搜索延迟及内存如何变化？需固定夹具、机器和生产构建后采样，不能从竞品宣传得出速度排名。
- U3：两条完整保存路径在快速连续操作、笔记/账目同时更新和退出时是否产生旧快照覆盖或未落盘？源码显示需检查的边界，本轮未复现数据丢失。
- U4：保持现有关系结果的前提下，缓存正文特征能节省多少时间？全局文档频率变化会影响 TF-IDF 权重，不能假定只重新计算被编辑节点即完全等价。
- U5：环境光、Canvas 绘制和布局各占多少 GPU/CPU？已有实际截图能证明外观，不能证明低配机器流畅或后台资源消耗。
- U6：图谱关系对自然中文的误连/漏连程度？需人工标注的小规模记录对，而不是随机汉字压力夹具。
